- [ ] E2E 2: `fc-` packets in DMs. A packet is `fc-` plus unpadded base64url, at most 1497 bytes (1996 characters), so it fits one 2000-character message. Byte 0 is a version, byte 1 a type (Hello, Init, Msg). Treat Discord like UDP with an attacker on the path: packets can be lost, reordered, duplicated, replayed or forged, so every packet is authenticated and safe to receive twice. The message list shows `fc-` messages instead of their raw text: Hello as "X wants to encrypt this DM" with an Accept button, and anything it can't decrypt as "Encrypted message". A lock toggle in the DM header turns encryption on. Never send Hello unless the user asks.
- [ ] E2E 3 (an encrypted DM works): PQXDH with X25519 and ML-KEM-768, then the Double Ratchet with ChaCha20-Poly1305 and HKDF-SHA-256. All primitives come from BoringSSL; the protocols are written in Jai from Signal's specs. ML-KEM-768 is chosen so Hello and Init each fit in one message. Prekeys stay unsigned until E2E 5, which protects against Discord reading DMs but not against it swapping keys. Hello carries the identity key, its Merkle proof and the prekeys; Accept answers with Init and the first message. Two traps. First: commit the advanced ratchet state to the database before the ciphertext is sent, with an outbox that resends after a crash; otherwise a crash reuses a message key. Second: decrypt each Discord message once and store its plaintext by message ID, plus your own sent plaintext, because history is fetched again and message keys are deleted after use. Test: two in-process clients over a fake carrier that drops, reorders, duplicates and replays packets. Bump the version byte freely while only a few people use it.

- [ ] Federation 1: authority logs (`FEDERATED.md` §6). Each identity, user or server, keeps an append-only BLAKE3 Merkle Mountain Range (MMR) of its authority changes: key rotations, addresses and certificates, owner changes and delegations. It also keeps a sparse Merkle tree of its current state. Chat messages never go in the log. The identity signs checkpoints: sequence, MMR size and root, state root, previous checkpoint, expiry. Batch changes into one checkpoint, because SLH-DSA signing is slow. The signed server record becomes the latest checkpoint, with one entry per address (IPv4, IPv6). Clients store the last checkpoint seen per root. They reject one that doesn't extend it (consistency proof), so a rollback fails. Tests: a forked history, a rollback, and a stolen signing key overridden by the recovery key.
- [ ] Federation 2: names (§4-5). An identity signs delegations "label → child root". Each has a scope: one name or a subtree, record types, whether it can delegate further, and expiry. Trust flows down only. Trusting A resolves `A/community/chat`. Trusting C never means trusting B or A. A parent can repoint its own label but never rewrite a child you pinned directly. Children can gain parents later, and cycles are allowed. The resolver caps depth, nodes visited, proof size and time. Names are NFC-normalized and casefolded, with confusable labels flagged. Uses: a community grouping several servers, readable invite names, and local aliases.
- [ ] Federation 3: the DHT (§8-9). Kademlia over QUIC (vendored ngtcp2) on the same authenticated transport as Hosting 5 (`IP:port:magic:root`). Nodes are hosts only. It stores signed checkpoints keyed by root and content-addressed chunks keyed by BLAKE3 hash: server details and history fragments. Every response is untrusted until verified. Node ID = BLAKE3(root, proof-of-work nonce), so an attacker can't cheaply grind keys to land next to a target. Bootstrap never needs the DHT itself: bundled peers, cached peers, invite hints and manual addresses. Important lookups go along several disjoint paths and compare checkpoints. A private server's record is encrypted under a key derived from its root. Invites fall back to the DHT when the hint fails.
- [ ] Federation 4: harden the DHT (§10-11). Use a Bitcoin-style address manager: separate tried and new peers, keep anchor peers across restarts, test a peer before evicting it, and pick peers randomly. Cap peers from one ASN (network operator) and IP prefix in each bucket and overall. Records have size caps (about 64 KB), expiry, per-node storage and publish-rate quotas, and a hash blocklist. Note in the code that per-key quotas don't stop Sybils on their own. Test: a simulated eclipse attack fails to isolate a node.
- [ ] Federation 5: TTL plus push invalidation (§12). Relays found through the DHT forward signed checkpoints to subscribers on renewable leases. Relays are untrusted: they can delay or drop updates but can't forge them. A cached resolution records its delegation path and revalidates when any link's checkpoint advances. TTL still bounds staleness, so security never depends on a notice arriving. On reconnect a client sends its last checkpoint and fetches what it missed. Test: relays that drop notices and crash.
- [ ] Federation 6: witnesses (§7). Hosts witness the checkpoints of servers they talk to and gossip them. Two signed checkpoints at the same position are equivocation evidence. Keep that evidence and pass it on. The server shows "this server has two histories" and stays blocked until its recovery key signs a continuation. This replaces the copied-file "same sequence number" warning in Hosting 3. Never resolve a fork by taking the higher sequence number.

- [ ] Security: the media demuxers trust sizes from the file, so any user's crafted attachment can crash or corrupt fastcord when it's viewed or played.
