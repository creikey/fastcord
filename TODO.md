- [ ] Keys, the rest (needed by Hosting 2; `FEDERATED.md` §26):
  - Key changes are rotate records in the identity's log (Federation 1), never a new root. Only the recovery key signs rotate records, for any key. An everyday key can't rotate itself or any other key, so a thief who steals it can't rotate your keys on every server. There are no revoke records, only rotations.
  - Device certificates are signed by the signing key. They add a device; they don't rotate anything. Each names what the device may do: never add devices, rotate keys or transfer ownership. Each expires within weeks and is renewed automatically, since there are no revoke records: a lost device dies at expiry (`FEDERATED.md` §5 capability rules).
  - A zero policy leaf means this v1 policy. The recovery key can sign a move to a stricter policy, such as 2-of-3 recovery keys. Nothing can loosen a policy. Freeze this format now, so later steps never change anyone's identity.
  - Joining a server reuses the default keypair. Settings > Keys, also reachable from the user menu, lists keypairs and lets you create, rename, export and import them, and choose which one each server uses.
  - Keys must survive fastcord bugs and settings resets. They live in `keys` beside `<state>`, never inside it, so deleting settings or `<state>` never touches them.
    - At rest, keys (and `fastcord.db`'s database key) are wrapped with the OS keystore: DPAPI on Windows is done; Keychain (macOS) and libsecret (Linux) are not (`src/keys` `wrap`).
  - A failed key save at startup is only logged (`identity.jai`), so the next start makes a different identity. Show it, with the reason, in Settings > Keys.
  - Bug: keys that exist but can't be opened are silently replaced. `keys.load` skips every file it can't read or unwrap, and `identity_start` then makes a new "Default" identity whenever the list is empty. Causes: DPAPI's master key is gone after a Windows reinstall, a restore onto a new PC, or an admin password reset; or antivirus or a backup locked the file at startup. The user loses every self-hosted account without a word. Make a new identity only when the folder holds no `.key` files at all. Otherwise say "Your keys can't be opened", give the reason, and retry, never auto-create.
  - DPAPI ties both copies to this Windows user's master key, so the second copy doesn't help against that loss. Only a portable backup does: the recovery-key export below, or a passphrase-encrypted export. Offer it before the first server join. The passphrase goes through scrypt (BoringSSL's `EVP_PBE_scrypt`) into an AEAD key, and the export names its root so import checks that the keys match it.
  - The recovery key starts beside the signing key, where a thief would take both. Settings offers to export it, as a file or a printout, and then remove it from disk.
  - Later:
    - Easy device sync, by QR code or an encrypted export. The new device shows the QR (a one-time public key) and the old one encrypts the keys to it, so a photographed QR leaks nothing.
    - Password-manager storage.
    - Passkeys. Research first: passkeys are P-256, classical and usually non-exportable, so they can be an extra login key, never the identity.
- [ ] Hosting 2: `fastcord -serve`. One SQLite file per server, speaking the subset of Discord's gateway and REST that fastcord uses. Text channels and invites first. Hosting 1-4 need only Keys, not E2E: self-hosting ships first, and server roots and signed records plug in at Hosting 5. Each server file holds a random 128-bit server ID. Transport: TLS 1.3 with X25519MLKEM768, ALPN `fc/1`, and the server ID as SNI. The certificate is self-signed and long-lived. Invites are `fc://<cert hash>@<host:port>/<server ID>/<code>`, with IPv6 in brackets, and joining pins that hash, with no certificate authority. Until Hosting 5, changing the certificate breaks existing pins, so the host tab warns before allowing it. Accounts are keys, with no passwords (`FEDERATED.md` §26). Joining sends your public key with the invite code, which uses up one of the invite's uses, and the key becomes your account. Logging in signs a challenge that binds the TLS exporter, the ALPN and the server ID, so a login can't be relayed to another server or protocol. Signing runs off the UI thread, since SLH-DSA is slow. - [ ] Federation 1: authority logs (`FEDERATED.md` §6). Each identity, user or server, keeps an append-only BLAKE3 Merkle Mountain Range (MMR) of its authority changes: key rotations, addresses and certificates, owner changes and delegations. It also keeps a sparse Merkle tree of its current state. Chat messages never go in the log. The identity signs checkpoints: sequence, MMR size and root, state root, previous checkpoint, expiry. Batch changes into one checkpoint, because SLH-DSA signing is slow. The signed server record becomes the latest checkpoint, with one entry per address (IPv4, IPv6). Clients store the last checkpoint seen per root. They reject one that doesn't extend it (consistency proof), so a rollback fails. - [ ] Federation 2: names (§4-5). An identity signs delegations "label → child root". Each has a scope: one name or a subtree, record types, whether it can delegate further, and expiry.
